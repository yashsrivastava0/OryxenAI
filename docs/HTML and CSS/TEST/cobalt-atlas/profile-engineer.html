01 / Infrastructure
4.2MEvents per second

Abstract artwork — not a product screenshot.

01 / The problem

Three schedulers, three failure modes.

Teams had each built their own scheduler on cron, Redis lists and a spreadsheet. Retries, ordering and visibility were inconsistent, and nobody could answer what had run.

02 / The approach

Make the database the queue.

Jobs live in PostgreSQL and are claimed with row-level locking, so one consistent store gives durability, observability and transactional enqueue.

  • SKIP LOCKED claiming with leases and heartbeats
  • Exponential backoff and a dead-letter view
  • OpenTelemetry traces from enqueue to completion
03 / Outcome4.2M

events per second sustained in load tests, with three legacy schedulers retired in this fictional program.

02 / Machine learning

Abstract artwork — not a product screenshot.

01 / The problem

Training and serving drifted apart.

Features were re-implemented for each environment, so models behaved differently online than they had during evaluation.

02 / The approach

One definition, two runtimes.

A declarative feature spec compiles to batch jobs and a low-latency online path, with point-in-time correctness enforced by tests.

  • Declarative specs with typed schemas
  • Backfills with point-in-time joins
  • Online reads under 5 ms at p99
03 / Outcome-60%

fewer training and serving mismatches reported by model owners in this fictional program.
