# Operation

Build the editable Discovery brief.

## Inputs

You receive:

- The validated normalized profile.
- The validated fact registry.
- Conflicts.
- Discovery questions.
- User answers.
- Explicit skips.
- Automatic presentation decisions.
- Requested output language.
- Product constraints.

## Required process

1. Use only validated facts and explicit user-provided information.
2. Incorporate the user's answers.
3. Apply automatic choices only where permitted.
4. Resolve conflicts only when the user answer clearly resolves them.
5. Preserve unresolved conflicts when they remain material.
6. Select one primary target role when possible.
7. Select a small set of strongest projects using evidence and target-role
   relevance.
8. Separate project scope from personal contribution.
9. Record deliberate omissions.
10. Produce a strategic brief, not final website copy.

## Brief quality

The brief should be useful to a future Content Architect and should
clearly state:

- Who the portfolio targets.
- What professional goal it serves.
- How the person should be positioned.
- Which projects or experience should lead.
- What strengths to emphasize.
- What information to omit.
- What confidentiality restrictions apply.
- What tone and presentation preferences apply.
- What CTA or contact action is appropriate.
- What material uncertainty remains.

## Restrictions

Do not create a hero headline, full About section, complete project case
study, visual component plan, or code instructions.

Do not create new professional claims to make the brief sound stronger.

If the profile is sparse, recommend a shorter portfolio rather than
inventing sections.
