# Durable generation redelivery and caller-specific declines

This change centralizes `cannot_complete` extraction while leaving generation, integration polish, and final verification in control of their own retry policies. It also persists per-unit continuation state, adds request-transition receipts, distinguishes automatic redelivery from explicit retry, and deduplicates generation calls. Final verification still routes declines through its independent `RepairBudget`. The retry boundary is not yet crash-safe: explicit retry can replay the failed model cache, and pending source evidence can diverge from the database projection.

Watch for: **[confirmed, P1] explicit retries replaying cached failed responses**, **[confirmed, P1] pending-proposal ledger/projection split-brain after process death**, **[confirmed, P2] request transitions being counted twice**, and **[confirmed, P2] rejected integration-polish source surviving an explicit retry**.

**Verdict**: NEEDS_CHANGES

## High-level view

The shared extractor is policy-neutral: generation chooses original-operation replacement or repair from candidate completeness, integration polish preserves accepted source and re-reviews, and final verification retains its separate decline exception and budget.

**[confirmed]** Automatic redelivery can resume persisted request/repair intent, but explicit retry resets that intent without advancing model-call identity and erases request receipt IDs while retaining their cumulative count. The same cached failure or request can therefore be replayed as though it belonged to a fresh attempt.

**[confirmed]** Pending evidence remains one mutable file per unit. Original-operation replacement can delete the database-referenced file before its successor is durable, while checkpointed owner units can retain rejected integration-polish evidence across an explicit retry.

**[confirmed]** Generation and owner-polish calls use the new receipt deduplicators, but whole-site integration review still appends receipts directly, leaving integration redelivery non-idempotent.

## Explicit retry recreates the failed cache key

**[confirmed, P1]** `CodeGeneratorDevelopmentService.generate` resets unfinished units to request round zero, repair round zero, original operation/profile, no diagnostics, and no pending proposal, but preserves `generation_id` and the call ledger (`development_service.py:877-899`). `CodeGeneratorGenerationOrchestrator._model_result` keys cached responses only from generation, unit, operation, prompt, context, and request round (`generation_orchestrator.py:2876-2880`).

After a no-candidate decline exhausts its budget, the reset reconstructs the first failed context: diagnostics are archived, pending evidence is gone, counters are zero, and the checkpoint is unchanged. The explicit retry therefore loads the old `cannot_complete`; each later round can replay the same cached sequence without reaching the provider. Advance a durable attempt epoch only for explicit retry and include it in both call-cache and attempt-record identities. Not tested: exhaust a decline, invoke `generate()` again, and assert that the new attempt's first call is not a cache hit.

## Pending proposal replacement can strand durable state

**[confirmed, P1]** In `CodeGeneratorGenerationOrchestrator._run_unit`, a partial/no-candidate decline returning to the original builder unlinks the currently referenced ledger and clears only the in-memory projection before `_apply_changes` writes a successor (`generation_orchestrator.py:1816-1826`). Process death after the unlink leaves the database pointing at a missing record.

`_record_pending_diagnostics` also overwrites the same fixed-path record before the updated `PendingSourceProposal` reaches the database (`generation_orchestrator.py:460-481`). Process death there leaves old database metadata beside new filesystem metadata. Immutable attempt-versioned records, followed by a projection CAS and deferred cleanup, close both windows. Not tested: terminate between ledger write/delete and projection persistence, then redeliver.

## Request replay loses its idempotency receipt

**[confirmed, P2]** Explicit retry clears `request_receipt_ids`, `pending_request`, and unit request round but leaves `GenerationProjection.request_rounds` cumulative (`development_service.py:877-899`). Replaying the same cached request no longer finds its receipt and increments the count again (`generation_orchestrator.py:1762-1772`); `_resolve_requests` passes that inflated count to the acquisition ceiling (`generation_orchestrator.py:3093-3095`, `acquisition_validators.py:180-183`).

This can block the retry that must finish an acquisition which failed before committing a receipt. Pre-change runs interrupted in `acquiring` deserialize with no `pending_request` or receipt IDs and follow the same double-count path. Preserve receipt IDs across explicit attempts, track the active attempt's round separately, and add compatibility handling for legacy `needs_resources`/`acquiring` projections. The current integration test covers cancellation after the new reservation exists, not either missing-receipt case.

## Checkpointed owners keep rejected integration-polish source

**[confirmed, P2]** The new explicit retry reset only touches non-checkpointed units (`CodeGeneratorDevelopmentService.generate`, `development_service.py:877-889`). Integration polish stores its `pending_proposal` on the original owner, which is already checkpointed. If a polish candidate fails source checks and a later call declines, rollback restores accepted source but the owner retains the rejected proposal.

On the next explicit attempt, `_review_and_polish` loads that proposal and seeds `pending_files` from it (`generation_orchestrator.py:2170-2175`), allowing prior rejected bodies to merge into the next repair. Reset transient request/repair/proposal fields for all units while preserving checkpoint status and hashes. Not tested: fail owner polish, decline the follow-up, explicitly retry, and verify the first new polish has no prior pending bodies.

## Whole-site review receipts still append on redelivery

**[confirmed, P2]** The new `_record_context_receipt` and `_record_call_receipt` helpers protect generation and owner-polish replay, but `CodeGeneratorGenerationOrchestrator._integration_review` still appends both records directly (`generation_orchestrator.py:2599-2603`). If a review is persisted and the worker exits before polish completes, redelivery reruns that round and stores duplicate receipt IDs, inflating call evidence and bypassing the new collision checks. Use the helpers here as well and test V4/session redelivery immediately after `_persist_integration_review`.
